## ١. الاكتشاف الجذري: الإنتاج بلا إعدادات

`lib/firebase.ts` يحمل قيماً احتياطية حتى ينجح `next build` بلا أسرار — يحتاجها CI:

```ts
apiKey: process.env.NEXT_PUBLIC_FIREBASE_API_KEY ?? "AIzaSyBuildPlaceholderKeyForCI0000000000"
```

مشروع Vercel كان يحمل **متغيّرين اثنين فقط** (`FIREBASE_DATABASE_URL` و
`NEXT_PUBLIC_FIREBASE_DATABASE_URL`، كلاهما من ٢٢ مايو). فكل بناء إنتاجي كان يطبع
المفتاح الوهمي في حزمة المتصفح.

**لماذا لم يظهر:** `NEXT_PUBLIC_*` تُحقن وقت **البناء** لا وقت التشغيل. لا شيء يفشل
في البناء، ولا في النشر، ولا في CI. الأثر الوحيد أن Firebase يرفض كل تسجيل دخول بـ
`auth/api-key-not-valid` — وهو كود لم تكن صفحة الدخول تعرفه، فيسقط إلى
«حدث خطأ غير متوقع» ويُقرأ ككلمة مرور خاطئة.

### التشخيص في ثوانٍ (احفظ هذا)

```bash
# اسحب أي chunk من الموقع الحيّ وابحث عن المفتاح الوهمي
curl -s https://joker-dashboard.vercel.app/login | grep -o '/_next/static/chunks/[^"]*\.js' | head -1
```

وجودُه يعني مشكلة إعدادات لا مشكلة كود. الآن يعلن عن نفسه: `lib/firebase.ts` يصدّر
`isFirebaseMisconfigured`، وصفحة الدخول تقول «النظام غير مهيّأ بشكل صحيح على الخادم»
عند التحميل بدل انتظار محاولة دخول محكومة بالفشل.

### ما نُفِّذ على Vercel

أُضيفت ثمانية متغيّرات لبيئة Production and Preview، ثم Redeploy بلا build cache:

```
NEXT_PUBLIC_FIREBASE_API_KEY · AUTH_DOMAIN · PROJECT_ID · STORAGE_BUCKET
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID · APP_ID · MEASUREMENT_ID
FIREBASE_PROJECT_ID
```

**تحقّق مستقل:** `identitytoolkit` ردّ `INVALID_LOGIN_CREDENTIALS` على حساب وهمي —
أي أن المفتاح صالح ووصل الطلب — و`lastSignInTime` لحساب المالك تغيّر إلى نفس اليوم.

### ما زال ناقصاً على Vercel

| المتغيّر | الأثر ما دام ناقصاً |
|---|---|
| `FIREBASE_CLIENT_EMAIL` | Admin SDK معطّل |
| `FIREBASE_PRIVATE_KEY_B64` | Admin SDK معطّل |
| `RESEND_API_KEY` | لا إيميلات |
| `RESEND_FROM_EMAIL` | اختياري |

القيم في `.env.local`. أضفها ثم **Redeploy بلا build cache**.

**الأثر الدقيق:** الدخول والقراءات تعمل — قراءات المشتركين والتحليلات تذهب من المتصفح
إلى Firestore مباشرة وتحكمها `firestore.rules`. أما `hasAdminCredentials()` فترجع
`false`، ومسارات API تتدهور **بصمت**: `/api/sessions` يرد `200` بقائمة فارغة و
`skipped: true`، فتعرض صفحة الجلسات أصفاراً بينما أنت مسجّل دخول. الرمز `200` هنا ليس نجاحاً.

## ٢. أعطال مالية اكتُشفت أثناء كتابة الاختبارات

`app/api/subscriber-operations/route.ts` — ١٠٨٢ سطراً وثماني معاملات مالية بلا أي
تغطية، وكانت أكبر مخاطرة متبقية في وثيقة ٢ أغسطس. الحسابات استُخرجت إلى
`lib/subscriberFinance.ts` (نقية، بلا Firestore وبلا قراءة `Date.now()` ضمنية).

### أ. `Number(null)` يبطل حارس سعر الصرف

```ts
Math.max(asNumber(rate, 1), 0.000001)
```

`Number(null)` و`Number("")` و`Number([])` كلها `0` — وهو **رقم منتهٍ**، فشرط
`Number.isFinite` يمر والقيمة الاحتياطية `1` لا تُستخدم أبداً. السعر يهبط إلى
`0.000001`، فالقسمة عليه تضرب المبلغ في مليون: **دفعة ٥٠$ تُسجَّل ٥٠ مليون**.

غير قابل للاستغلال اليوم لأن مخططات Zod ترفض `null` قبل الوصول. أُصلح في
`normalizeExchangeRate` على أي حال: الحارس لا يصح أن يعتمد على مُتحقِّق في طبقة فوقه.

### ب. حساب التواريخ يخلط UTC بالمحلي

`new Date("2026-06-10")` يُفسَّر منتصف ليل **UTC**، بينما `setDate`/`getDate` تقرأ
مكوّنات **محلية**. `addDays` و`daysUsed` و`remainingDays` كانت تخلط الاثنين: صحيحة
في UTC (حيث يعمل Vercel) وخاطئة بيوم كامل غربه. أُعيدت كحساب UTC خالص، والاختبارات
تمر في أربع مناطق زمنية.

> **مفتوح — قرار عمل لا إصلاح تقني:** `todayString()` يقرأ تاريخ UTC. بين منتصف الليل
> و٢–٣ صباحاً بتوقيت مصر/فلسطين تُسجَّل العمليات بتاريخ **الأمس**. نافذة ضيقة لكنها
> تمسّ تواريخ الدفع والانتهاء.

## ٣. تشديد الإنتاج

- **`unsafe-eval` أُزيل من CSP الإنتاجي.** كان يُشحن في `script-src` على كل رد. يحتاجه
  React Refresh في التطوير وحده؛ شحنه في الإنتاج يسمح بتنفيذ نص محقون ككود — وهو
  تحديداً ما تمنعه السياسة. تُحقِّق منه صفحة إنتاج حقيقية بلا أخطاء كونسول.
- **`images.domains`** محذوف في Next 16 وكان يحمل `cdn.example.com` → `remotePatterns`.
- **`.github/workflows/ci.yml`** — lint · typecheck · jest · بناء إنتاج، مع خطوة تعيد
  تحليل ملفات Firebase منعاً لعودة عطل تعليقات `//`.
- **قواعد وفهارس Firestore** سُجّلت في git ونُشرت (٦٠ فهرساً). النسخة المسجّلة كانت
  القديمة المعطوبة؛ الريبو كان متأخراً عن الواقع.

## ٤. صفحة المستخدمين

### صفوف شبح

حذف مستخدم من كونسول Firebase يزيل هوية Auth ويترك وثيقة `/users`. الصفحة كانت
تعرض تلك البقايا كموظفين حقيقيين: «حنان» مرتين، «ميدو» مرتين، ثمانية مستخدمين
مقابل ستة حسابات، ومالك ثالث لا يستطيع تسجيل الدخول.

**محاولة أولى فاشلة — تُذكر لأن الدرس فيها:** فُلترت الوثائق التي بلا `email` بحجة أن
الدخول بالإيميل. البيانات تخالف ذلك — المالك «عبدالله طلبة» بلا `email` على ملفه وله
حساب حيّ، والمالك «Medo» بلا `createdAt`. **لا حقل على الوثيقة يجيب السؤال.**

الحل الصحيح: `/api/users/auth-uids` يعدّد Auth على الخادم ويرجع الـ uids الموجودة
فعلاً. ويسقط **مفتوحاً** بالتصميم — يرجع `uids: null` عند غياب بيانات Admin بدل خطأ،
والصفحة لا تخفي شيئاً حينها. إظهار صف قديم أهون بكثير من إخفاء مسؤول حقيقي.

### ثلاثة أعطال جذرها واحد

`app/globals.css` يعطي كل `input` و`select` مجرّد `width:100%` و`height:44px` وحدوداً
و`border-radius:12px`. فترتب عليه:

| العَرَض | الإصلاح |
|---|---|
| كل اسم داخل `<input>` بلا `disabled` — يبدو حقل إدخال، ويسمح لمدير بلا `users.manage` بالكتابة ثم يرفضه الخادم بـ 403 | نص، إلا لمن يملك التعديل فعلاً |
| شارة الدور بجانب `select` بنفس القيمة، والحالة كذلك | عنصر واحد لكل منهما |
| فلتر الحالة يأخذ سطراً كاملاً | أبعاد صريحة على كل عناصر الفلترة |

وأيضاً: خمس بطاقات إحصاء متساوية (إحداها صفر دائماً) صارت شريطاً واحداً، وزر الإجراءات
صار يقول «الصلاحيات»، والحالة `deleted` كانت تُطبع خاماً بالإنجليزية بلا تنسيق، والجدول
يتحوّل إلى بطاقات معنونة تحت ٧٦٨px عبر `.jk-stack-table` بدل التمرير الأفقي.

## ٥. نموذج الصلاحيات — سقف لكل دور

كان في النظام **شيئان يُسمّيان دوراً**، لكل منهما جدول صلاحيات، ولا قاعدة تحسم أيهما يفوز:

```
role     (owner | admin | employee)      ← السلطة: مَن يدير مَن
employeeRole (sales | followup | team_leader)  ← الوظيفة: ماذا تعمل
```

و`authStore` كان يختار بينهما **حسب وجود حقل `granularPermissions` في الوثيقة** — فنفس
السؤال يعطي جوابين حسب شكل السجل.

### الانقلاب

`EMPLOYEE_ROLE_PERMISSIONS.sales` منح `subscribers.delete` و`payments.refund` و
`subscriptions.withdraw`. و`DEFAULT_GRANULAR_PERMISSIONS.admin` لم يمنح أياً منها.
و`sales` هو **الافتراضي** في نموذج إنشاء موظف — فالموظف الجديد العادي يتفوّق على مدير.

### الحل

```
effective(user) = ROLE_CEILING[role] ∩ (override ?? JOB_PRESET[employeeRole] ?? ROLE_DEFAULT[role])
```

`ROLE_CEILING` أقصى ما يملكه أي حساب في مستوى السلطة ذاك، مهما قال preset أو تخصيص.
التقاطع يجعل الانقلاب **مستحيلاً بنيوياً** لا محكوماً بالانضباط.

| | مالك | مدير | موظف |
|---|:---:|:---:|:---:|
| حذف مشترك | ✓ | ✓ | ✗ |
| استرجاع دفعة | ✓ | ✓ | ✗ |
| انسحاب اشتراك | ✓ | ✓ | ✗ |
| تحليلات وتصدير | ✓ | ✓ | حسب الوظيفة |
| إنشاء حساب · تغيير دور | ✓ | ✗ | ✗ |
| تفعيل/تعليق حساب قائم | ✓ | ✓ | ✗ |

`canDoGranular` و`hasServerPermission` ومُحدِّدات `authStore` الثلاثة تمر كلها من
`effectivePermissions` — فالعميل والخادم يجيبان الجواب نفسه.

**الاختبار كشف انقلاباً ثانياً لم يكن في التشخيص:** السقف وحده لم يكفِ. **افتراضات**
المدير ظلّت أضعف من preset الموظف (بلا `subscribers.delete` وبلا `analytics.export`،
وكلاهما يمنحه `team_leader` و`sales`). المالك والمدير صارا يبدآن من سقفهما، ومَن يجب
أن يملك أقل يأخذ تخصيصاً صريحاً.

## ٧. أدوات جديدة

```bash
npm run audit:accounts                                   # تقرير
node scripts/audit-accounts.mjs --disable someone@x.com  # تعطيل
node scripts/audit-accounts.mjs --enable  someone@x.com  # تراجع
```

يعطّل ولا يحذف: الـ uid مرجعيّ في `convincedByUid` على المشتركين والدفعات، وقواعد عزل
الموظفين تقرأ ذلك الحقل، فالحذف يُيتّم السجلات بلا رجعة. ويلغي refresh tokens أيضاً —
`updateUser` وحدها تترك توكناً صادراً صالحاً حتى ساعة.
